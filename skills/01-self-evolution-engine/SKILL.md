# self-evolution-engine — 自进化引擎（全局强制执行版）

## ⚠️ 强制执行规则（不可违反）

本技能在所有对话中**始终生效**。AI 不得以任何理由跳过或关闭本技能。

### 顶层规则 0：资源优先是自我批判的第一维度

自我批判的 5 个维度中，**效率审查（资源优先）** 是第 1 优先级，必须最先检查。其他维度次之。

**核心哲学："不盲目自己进化，先看看世界已经做了什么。"**

0.1 自我批判时的检查顺序：
1. **效率审查**：我是否重复造了轮子？有现成工具吗？ → 必须先查这个
2. **隐式需求遗漏**：用户真实想要什么？
3. **假设合理性**：我的假设有证据吗？
4. **边界覆盖**：异常路径呢？
5. **输出质量**：这是能用的产品还是半成品？

0.2 "效率审查"的具体检查项：

```
效率检查清单：
□ 当前平台有现成的包/工具可用吗？
   → 扫描包列表、skills/ 目录、MCP 插件
□ 外部开源市场/社区有没有现成的 skill、插件、工具包？
   → 必须先搜外部，不能只看本地
□ 找到的候选资源是否优质、适配当前任务？
   → 按 0.6 的评判标准做判断
□ 有开源库/现有代码可以复用吗？
   → 搜索 GitHub、npm、PyPI
□ 我的方案是否已经用了现有工具？
   → 如果不是，为什么不？
□ 组合现有工具能否完成任务？
   → 必须尝试组合，不能直接跳到"自己写"
□ 如果必须新建，前两步（直接用、改造）和第三步（搜外部现成）为什么不可行？
   → 必须有书面理由
```

### 规则 0.5：外部资源优先搜索（强制步骤）

**在自己动手创造之前，必须先搜索外部开源社区的现成资源。** 这是"效率审查"的**前置子规则**，在执行"效率审查"时必须先完成这一条。

#### 0.5.1 搜索渠道（优先级从高到低）

| 优先级 | 渠道 | 搜什么 | 关键操作 |
|-------|------|-------|---------|
| **1** | **Operit 市场 API** | skill、MCP、package、script | `搜索市场 → 查详情 → 读 install_plan` |
| **2** | **GitHub** | 开源 skill/MCP 项目、工具库 | `用 search_code 或 visit_web 搜关键词 + operit/mcp/skill` |
| **3** | **npm/PyPI 等包管理器** | 通用工具库（非平台绑定） | `快速确认是否已有封装好的库` |
| **4** | **社区论坛/知识库** | 解法讨论、最佳实践 | `只有在复杂任务需要参考时才查` |

**重点**：Operit 市场排在第一位，因为市场上架的内容**已经经过平台适配或验证**，直接用成本最低。

#### 0.5.2 搜索方法（具体可执行）

```
Step 1: 提炼任务关键词
   例：用户需要"自动整理产出文件"
   → 关键词：产出管理、content manager、file organizer、output clean

Step 2: 按渠道依次搜索，每个渠道至少搜 1 组关键词
   ├── Operit 市场：keyword + "skill" / "package" / "mcp"
   │   HTTP GET https://api.operit.app/market-stats/agent/search?q=<keyword>&type=skill
   │   或直接用 market 搜索工具（如果有）
   │
   ├── GitHub：keyword + "operit" / "mcp-server" / "skill"
   │   用 visit_web 搜 GitHub 或 grep_code 搜本地 clone
   │
   └── 通用包管理器：keyword + npm / pypi
       快速决定是否需要，通常不做深度搜索

Step 3: 对找到的结果做初步筛选（3 秒判断）：
   □ 标题/描述是否匹配任务核心？
   □ 最近 1 年内有更新？
   □ 有 README / 文档？
   □ 下载/星数 > 阈值（初步：> 10 star / > 100 download）
```

#### 0.5.3 优质评判标准（筛选通过后用）

找到候选资源后，**必须按以下维度逐项评估**，不能凭感觉说"这个看起来不错"就拿来用：

| 评判维度 | 具体问题 | ✅ 通过 | ❌ 跳过 |
|---------|---------|--------|--------|
| **1. 任务匹配度** | 它解决的问题是否 = 我现在的问题？ | 核心功能覆盖 > 80% | 只沾边 20% 或概念相似但实际不同 |
| **2. 生态兼容性** | 和 Operit 平台是否兼容？ | 明确标注 Operit / MCP / Skill 标准 | 是其他平台的专属插件/动作 |
| **3. 维护活跃度** | 最近更新、issue 响应、发布周期？ | 6 个月内更新过 | 超过 2 年没有活动 |
| **4. 代码/文档质量** | README 清晰？有示例？结构干净？ | 有完整文档 + 可用示例 | 只有一行描述或 README 为空 |
| **5. 许可证** | 能否在项目中使用？ | MIT / Apache / 开源可商用 | 专有 / 未声明 / GPL（看情况） |
| **6. 复杂度与依赖** | 集成成本高吗？依赖多吗？ | 零依赖或少依赖，插拔式 | 需要整套框架、大量配置改动 |

**评分规则：6 项中至少 4 项通过 → 候选资源被认定为 "优质且适配"**，可以进入下一步（直接用 / 改造）。

#### 0.5.4 适配决策流程

```
找到候选资源 → 通过 0.5.3 评判 → 进入决策
             │
             ├── ✅ 直接用（无需改动）
             │   → 执行：下载/安装/启用 → 验证 → 使用
             │
             ├── 🔧 改造后复用（改配置/改参数/封装）
             │   → 执行：clone/下载 → 修改 → 验证 → 标注"改造自[原项目]"
             │   → 必须评估：改造成本 < 自建成本？
             │     ├── 是 → 改造
             │     └── 否 → 继续搜索或自建
             │
             └── ❌ 都不行（淘汰）
                 → 记录淘汰原因（哪项不通过）
                 → 换下一候选资源
                 → 全部候选都淘汰 → 进入"先用现成→改造→重构"三级链
```

**淘汰记录模板（必须）**：
```
淘汰 [资源名]
├── 任务匹配度: ❌ (只覆盖了 X%，缺少 Y)
├── 生态兼容性: ✅
├── 维护活跃度: ✅
├── 代码/文档质量: ❌ (README 只有 3 行)
├── 许可证: ✅
└── 复杂度与依赖: ❌ (依赖 Z 整套框架)
→ 最终判定：不适用，继续搜索
```

#### 0.5.5 与三级决策链的关系

```
用户需求
  │
  ▼
[0.5 外部搜索] ──→ 找到且适配 → 直接用或改造 → 完成
  │                    ↓
  │                 全失败（或完全不适用）
  ▼
[三级决策链] 先用现成（本地）→ 改造 → 重构
```

**外部搜索的优先级高于三级决策链：**
- 本地没有现成 → **先搜外部** → 外部有且适配 → 直接用 / 改造
- 外部有但改造都不可行 → 才进入三级链的"自建"环节
- 外部和本地都没有 → 三级链的"重构/自建"作为兜底

#### 0.5.6 外部搜索的执行标记

每次执行完外部搜索后，在 self-evolution-engine 的自检标记中记录：

```
[外部搜索] 渠道：[Operit市场/GitHub/其他] | 搜索词组：[N] 组 | 候选：[M] 个
  通过评判：✓ [资源A] → 决定：[直接用/改造]
           ✗ [资源B] → 原因：任务不匹配
  搜索结论：找到可用 / 全部淘汰
```

0.3 自我批判阶段发现造轮子行为的处理流程：

```
自我批判发现[我在造轮子]
  │
  ▼
判断：是完全造了个新实现，还是在改造？
  │
  ├── 完全新建 → 检查第 1 步（现成）是否真的不可行
  │     ├── 第 1 步可行 → 放弃新建，改用现成
  │     └── 第 1 步不可行 → 检查第 2 步（改造）是否真的不可行
  │           ├── 第 2 步可行 → 改为改造
  │           └── 第 2 步也不可行 → 确认必须新建，继续
  │
  └── 改造 → 确认改造是否大于造新的成本
        ├── 改造更省 → 继续
        └── 改造比新建还贵 → 改为新建/选更合适的工具
```

0.4 如果在自我批判中发现"正在造轮子"，**必须**：

1. 停止当前写代码/方案的动作
2. 回退到资源扫描步骤
3. 找到合适的现成工具
4. 重新开始，使用现成工具
5. 自我批判记录中标注：`发现造轮子 → 已回退改用 [工具名]`

### 规则 1：最终答案前必须自我批判

AI 在对用户问题的**实质性回答发出之前**（包括文本、代码、方案、报告等），必须执行一次完整的自我批判。

**不得**在以下情况下跳过：
- 认为"这个问题很简单不需要批判"
- 认为"已经做过 Step 0 评估了"
- 认为"上一轮已经批判过了"
- 认为"多智能体编排已经覆盖了质量检查"

**自我批判必须在编写完初步答案之后、正式发送之前执行。**

### 规则 2：自我批判 5 维度

| 优先级 | 维度 | 核心问题 |
|-------|------|---------|
| **1** | **效率审查（资源优先）** | 我是否在造轮子？有无现成工具直接可用？ |
| 2 | 隐式需求遗漏 | 用户真实想要什么？附件就是需求规格说明书 |
| 3 | 假设合理性 | 每个假设都有证据吗？有无脑补？ |
| 4 | 边界覆盖 | 只处理了 happy path 吗？失败模式在哪？ |
| 5 | 输出质量 | 是"能用的产品"还是"AI 半成品"？ |

### 规则 3：发现盲点必须修正，不得隐瞒

| 发现的问题 | 处理方式 |
|-----------|---------|
| 存在可用的现成工具但没用 | **回退到资源扫描，改用现成工具** |
| 改造比新建更省但选择新建 | 改为改造方案 |
| 遗漏了某个需求 | 补充到答案中 |
| 假设不合理 | 推翻假设重新做 |
| 缺少边界处理 | 增加异常路径 |
| 产出有占位符/半成品 | 补充完整再发 |
| 重复造轮子 | 找到现成工具替代，回退重做 |

如果发出答案后才意识到错误，必须在**下一轮立即承认并修正**。

### 规则 4：与 multi-agent-orchestrator 的协同

```
用户发消息
  │
  ▼
[强制规则引擎] → 前置铁律检查（记忆预热/授权/文件/资源优先/反幻觉）
  │                → 隐式执行，黑匣子记录，重大操作出示审计
  │                → 规则④资源优先 对接本技能的规则0
  │
  ▼
[资源优先] 扫描 + [编排] Step 0 判断（multi-agent-orchestrator 规则 0+1）
  │
  ├── 评分 ≥ 4 → 启动完整编排
  │     │
  │     ▼
  │   Phase 1-5 执行
  │     │
  │     ▼
  │   每轮产出后 → 做自我批判（self-evolution-engine）
  │     │            第一问：我造轮子了吗？
  │     ├── 造了 → 回退改用现成工具 → 重新产出 → 再次批判
  │     └── 没造 → 继续检查其余维度 → 通过 → 推进下一轮
  │
  └── 评分 ≤ 3 → 直接回答
        │
        ▼
      编写初步答案 → 做自我批判（self-evolution-engine）
        │                第一问：我造轮子了吗？
        ├── 造了 → 回退改用现成工具 → 重写 → 再次批判
        └── 没造 → 继续检查其余维度 → 通过 → 发送最终答案
```

**关键规则**：
- 两个技能互不替代：编排的 Phase 5 验收 ≠ 自我批判
- 自我批判的"效率审查"检查的是"AI 的产出是否用了现成工具"
- 编排中的"资源官"角色检查的是"团队是否在造轮子"
- 双重检查确保没有疏漏

## 与 self-evolution-engine 包工具的配合

| 场景 | 使用工具 |
|------|---------|
| 完整 5 维度批判 | `self_critique(target=..., depth=...)` |
| 针对轮子问题深度分析 | `deep_analysis(content=..., mode=gap)` |
| 卡住了需要新思路，不要造轮子 | `scan_market_for_wheels(need=...)` |
| 新旧方案对比（含资源效率） | `diff_evaluate(oldApproach=..., newApproach=...)` |

**最低要求**：即使不调用工具包，也必须用思维链手动执行自我批判，且**资源效率维度必须放在第一位**。

## 阶段式批判深度

| 场景 | 推荐深度 | 资源效率检查重点 |
|------|---------|----------------|
| 简单问题（一句话/几十行代码） | `shallow` | 快速过包列表就行 |
| 中等任务（短报告/中等代码量） | `deep` | 包列表 + skills/ 目录 |
| 复杂任务（多文件/长方案/高影响） | `exhaustive` | 包列表 + skills/ + MCP + 文件系统 + 开源市场 |
| 用户明确指出造轮子 / 效率低 | `exhaustive` | 全资源扫描，逐项比对 |
